# Privileged release test harness

Run `pwsh -NoProfile -File infra/release-privileged-tests.ps1` with the pinned Node image already available locally. The harness creates a disposable container, checks that it has no user-configured bind mounts, volumes or host network, PID, IPC, UTS or cgroup namespaces, copies the required test files into it, runs both tests and removes the container. Docker also provides its generated `/etc/hosts`, `/etc/hostname` and `/etc/resolv.conf` as file mounts; the tests do not write them. The scripts refuse direct execution without the harness marker. The marker and in-container checks are a guard against accidental host execution; the independently created Docker boundary provides isolation.

These tests use a fake `gh` verifier and fake `systemctl`; the process check inspects synthetic Node processes. They cover sealing and process-check behavior, but do not establish real GitHub attestation verification, a real systemd service lifecycle, production artifact identity, activation or rollback readiness.

`check-release-processes.sh <release-directory> <verified-manifest-sha256>` checks the root-owned release contents against the supplied digest and checks the four service process paths. Obtain the digest from the trusted attestation verification, not from the release itself. This identifies the sealed files and process entry points; it does not independently attest JavaScript already loaded into memory, prove that a process was started after sealing, or establish production readiness.
